Publish to HashBin from your app

Let your users store 256t content on HashBin.org directly from your web app. Users authorize your app via OAuth 2.0, and uploads are billed to their HashBin balance.

How it works Register your app and use hosted per-save approval without handling credentials. Opt into an allowance only when your app needs silent saves or delegated API access.

Why register your app?

Security

HashBin validates exact redirect URIs and PKCE transactions. Hosted saves return no credential; allowance tokens are constrained by DPoP when you use the SDK. Apps on one origin still share browser storage.

User trust

The consent screen shows your app name so users know exactly who is requesting access to their balance.

Spending controls

Users can set per-app monthly spending limits. Revocation and rate limiting are tracked per app.

Integration overview

  1. Register your exact redirect URI and get a public client_id. Acknowledge shared-origin risk where required; the client ID is not a secret.
  2. Save on a click: call SDK publish(). HashBin shows the app, safe document preview, CID, retention, exact price and balance.
  3. The user approves that save on HashBin. Your app receives a verified CID and never stores a HashBin credential.
  4. Need silent saves? Call authorize() to open allowance setup. The user reviews scopes, monthly cap, maximum file size and expiry on HashBin.
  5. Use save() for allowance uploads and set maxCostCents. The SDK binds tokens to a non-extractable browser key, checks CIDs and serializes refreshes.

Popup saves support up to 5 MiB; fragment redirects up to 512 KiB. Allowance defaults suggest $1/month, 1 MiB per file and a 30-day consent expiry. Access tokens last 15 minutes; new refresh tokens expire after seven idle days with a 90-day family maximum. SDK setup, callbacks and migration.

Example: app served from GitHub Pages

If your app is hosted on GitHub Pages, register your Pages URL as the redirect URI. Apps under one GitHub Pages host share storage, so prefer hosted approval. A single page can open the save popup and handle a fragment callback if redirect fallback is needed. A minimal version using the hosted SDK: 

<!-- https://your-username.github.io/your-repo/ (registered as the redirect URI) -->
<button id="publish">Publish "Hello, HashBin!"</button>
<script type="module">
  import { HashBinClient } from 'https://hashbin.org/sdk/hashbin.js';

  const hb = new HashBinClient({
    clientId: 'YOUR_CLIENT_ID',
    redirectUri: 'https://your-username.github.io/your-repo/',
    baseUrl: 'https://hashbin.org' // also the SDK default
  });

  // Redirect fallback: verify the result and restore your saved app state.
  if (location.hash.includes('hashbin_publish')) {
    const result = await hb.handlePublishCallback();
    console.log('Published:', result.cid);
    history.replaceState(null, '', location.pathname);
  }

  document.getElementById('publish').onclick = async () => {
    const result = await hb.publish('Hello, HashBin!', { contentType: 'text/plain' });
    if (!result.redirected) console.log('Published:', result.cid);
  };
</script>

For a persistent-allowance example with account API calls and drafts, see Textpad. For a new save-button-only app, start with the credential-free example above.

Available scopes

Scope Description
content:write Publish content, billed to the user's balance using their default retention period
content:extend Extend how long content is kept, billed to the user's balance
content:delete Delete content the user uploaded
uploads:read List the content the user uploaded
balance:read View the user's current balance (useful for pre-flight checks)
transactions:read Read the user's balance history
ratelimit:purchase Buy download allowances for content, billed to the user's balance
downloads:spend Pay for downloads from the user's balance, within their download caps
suppliers:read List the alternate suppliers the user registered
suppliers:write Register, change and remove alternate suppliers

Ask only for what your app needs: the user sees each permission, can uncheck any of them, and sets a monthly spending limit (required for anything that spends), a retention cap and an expiry. Your app can suggest ceilings with spending_limit (US dollars/month), max_retention_months and max_upload_bytes; the user can only tighten them. Refresh requests require client_id; rotated-token reuse revokes the entire grant. A token request may pass scope to get a token with fewer of the granted scopes. Account management (keys, apps, settings, deposits) is never available to apps.

About your client ID

Registering gives you a client ID that starts with app_. It's your app's public name, not a secret, so it can sit in your page source, your phone app, or a public repo.

Send it as client_id to /oauth/authorize and /oauth/token, or pass it as the clientId option in the SDK. HashBin uses it to show your app name on the consent screen, check that the redirect_uri is one you registered, apply the user's spending limit for your app, and make sure a code is redeemed by the app it was issued to.

Where's the client secret?

Many OAuth providers give you a client secret too. In standard OAuth, a server app sends its secret to the token endpoint to prove it is the real app (RFC 6749 §2.3.1).

Browser and phone apps can't keep a secret, because anyone can read their code. OAuth calls these public clients (RFC 6749 §2.1). Instead of a secret, they use PKCE: before sending the user to HashBin, your app makes up a random code verifier and sends only its SHA-256 hash. When it trades the code for tokens, it sends the verifier itself, and HashBin checks that it matches. Someone who steals the code doesn't have the verifier, so they can't use it.

HashBin uses PKCE for every app, including apps that run on a server, so there is no secret to keep: registering an app gives you only a public client_id.
