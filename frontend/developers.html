Publish to HashBin from your app

Let your users store 256t content on HashBin.org directly from your web app. Users authorize your app via OAuth 2.0, and uploads are billed to their HashBin balance.

How it works Register your app, get a client ID, and redirect users through a standard OAuth consent flow. Once authorized, your app can publish content on their behalf.

Why register your app?

Security

Redirect URI validation prevents authorization codes from being intercepted. Only your registered origins receive tokens.

User trust

The consent screen shows your app name so users know exactly who is requesting access to their balance.

Spending controls

Users can set per-app monthly spending limits. Revocation and rate limiting are tracked per app.

Integration overview

  1. Register your app below to get a client_id. Apps use PKCE and don't need the client_secret that is also shown (what's the difference?).
  2. Redirect users to /oauth/authorize with PKCE parameters.
  3. The user signs in (via their existing HashBin account) and approves your app.
  4. HashBin redirects back to your redirect_uri with an authorization code.
  5. Exchange the code at /oauth/token for an access token (1 hr) and refresh token (30 days).
  6. Use the access token to publish content via POST /api/content. Uploads use the user's default retention period, are billed to their balance, and return a content URL on https://256t.us/{cid}.

Client ID and client secret

When you register an app, HashBin gives you two values. They look alike, but they do different jobs and need different handling.

Client ID

What it is: your app's public name, starting with app_. It isn't a secret, so it can sit in your page source, your phone app, or a public repo.

Where it's used: as client_id in the /oauth/authorize request and again in the /oauth/token request. In the SDK it is the clientId option.

What it's for: it tells HashBin which app is asking. HashBin uses it to show your app name on the consent screen, check that the redirect_uri is one you registered, apply the user's spending limit for your app, and confirm that the app trading in a code is the one it was issued to.

Client secret

What it is: a random password for your app, starting with hbs_. HashBin shows it once, when you register, and keeps only a hash.

Where it's used: nowhere at the moment. HashBin's /oauth/token endpoint doesn't ask for or check a client_secret, and the SDK has no option for one.

What it's for: in standard OAuth, a server app sends its secret to the token endpoint to prove it is the real app. Browser and phone apps can't keep a secret, because anyone can read their code, so HashBin has every app prove itself with PKCE instead. If you keep the secret, treat it like a password: keep it on a server and never put it in page source, a phone app, or a repo.

Example: app served from GitHub Pages

If your app is hosted on GitHub Pages, register your Pages URL as the redirect URI. The simplest setup is a single page that starts sign-in, receives the user back from HashBin, and publishes. A minimal version using the hosted SDK: 

<!-- https://your-username.github.io/your-repo/ (registered as the redirect URI) -->
<button id="publish">Publish "Hello, HashBin!"</button>
<script type="module">
  import { HashBinClient } from 'https://hashbin.org/sdk/hashbin.js';

  const hb = new HashBinClient({
    clientId: 'YOUR_CLIENT_ID',
    redirectUri: 'https://your-username.github.io/your-repo/',
    baseUrl: 'https://hashbin.org' // without this the SDK calls your own site
  });

  // Back from the HashBin approval page: trade the code for tokens.
  if (new URLSearchParams(location.search).has('code')) {
    await hb.handleCallback();
    history.replaceState(null, '', location.pathname);
  }

  document.getElementById('publish').onclick = async () => {
    if (!hb.getTokens()) {
      await hb.authorize({ scopes: ['content:write'] }); // goes to hashbin.org
      return;
    }
    const result = await hb.publish('Hello, HashBin!', { contentType: 'text/plain' });
    console.log('Published:', result.cid, result.url);
  };
</script>

Available scopes

Scope Description
content:write Publish content, billed to the user's balance using their default retention period
content:read Check whether content exists and read its metadata
balance:read View the user's current balance (useful for pre-flight checks)

Third-party apps can only publish. Deletion, retention extension, and account management are not available through OAuth tokens.
