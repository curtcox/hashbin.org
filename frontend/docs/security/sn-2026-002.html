SN-2026-002: Manim Online ran linked code with its own shared origin

Manim Online runs code from the editor and from shared links in the browser. That code ran in a worker with the app's origin, https://curtcox.github.io, which every curtcox app shares. Code from a link could therefore use browser storage that belongs to that origin. No misuse is known. Since the 2026-10-28 rollout no curtcox app keeps a HashBin credential, which limited the exposure. Code now runs in the HashBin SDK sandbox with an opaque origin.

What was wrong

A shared link to a Manim scene rendered as soon as the page opened. The code ran in a classic Pyodide worker loaded from src/unified-worker.js. A worker loaded from the app's own files runs with the app's origin, so origin-scoped storage and same-origin requests were available to it, as they are to the app itself. On github.io that origin is shared by every project of the account.

Unlike Python Online, the worker removed no storage APIs, so the origin's storage was available to scene code as it was to the app.

How it was detected

The review asked one question of every app: where does untrusted code run, and with which origin? Both Python Online and Manim Online answered "a worker, with the app's origin". An automated check would have caught it sooner: the registered-app safety check now reports apps that start workers without the SDK sandbox.

How it can be demonstrated

The app's browser test runs a small program, with local test data only, that reports the origin its code runs with. Before the fix it reported the app's origin; after it, null, the opaque origin of a sandbox. The check now runs on every change as a regression test.

How it was fixed

  • HashBin-side: SDK v0.3.0 adds createSandbox(). It starts the worker inside an iframe with sandbox="allow-scripts", which gives it an opaque origin. Sandboxed frames are not controlled by the app's service worker, so the page fetches runtime files through its verified cache and hands them in. Any app using HashBin gets the same isolation without writing it.
  • App-side: Manim Online starts its worker with createSandbox(), loads its runtime through the sandbox proxy, adds the sandbox's bootstrap hash and blob: to its Content-Security-Policy, and vendors the exact v0.3.0 release, checked against its published hashes.
  • Rejected: removing storage APIs from the worker or Pyodide's JavaScript bridge. That narrows what code can reach, but it is not a boundary. An origin per app (a custom domain per project) protects sibling apps but not the app's own storage, so it complements the sandbox rather than replacing it.
  • Not needed: a prompt before running linked code was planned as a stopgap and dropped, because the fix shipped in the same release.

How to avoid it

Never run code from users or links with your page's origin, in a worker or in a frame with allow-same-origin. Use createSandbox(), or a separate origin you control. Treat every message from that code as untrusted data.

Lessons

  • "It runs in a worker" is not isolation. Ask which origin the code runs with.
  • An isolation mechanism belongs in HashBin once, not in each app. The registered-app safety check now looks for this pattern.
