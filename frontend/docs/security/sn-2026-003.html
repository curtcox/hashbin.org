SN-2026-003: JavaScript-readable tokens on shared origins

Browser apps stored HashBin OAuth access and refresh tokens in localStorage. On a host such as username.github.io, every app shares one origin, so any script running in any of those apps could read the tokens and use them elsewhere until they expired. Fixed for every app by HashBin-side changes; the curtcox apps no longer hold tokens at all.

Found2026-10-26, review of a sibling app's security model
Fixed2026-10-28: HashBin measures deployed from b36c126; client apps migrated the same day
AffectedSDK versions before v0.2.0 and any app storing tokens in Web Storage
SeverityHigh: stolen tokens gave offline access within the grant's spending cap
StatusFixed

What was wrong

Browsers isolate storage by origin (scheme, host and port), not by path. The hosted SDK kept tokens in localStorage, and the Origin header carries no path, so HashBin could not tell co-hosted apps apart. A bug or compromised dependency in any app on the origin exposed every other app's tokens.

How it was detected

A security review of one app asked what else could read its storage. The answer covered every HashBin client on the same GitHub Pages origin.

How it can be demonstrated

Not applicable now: no supported flow stores a bearer token in Web Storage. The browser tests in frontend/tests/browser-client-safety.spec.js check that a client completing a hosted save holds no tokens.

How it was fixed

  • HashBin-side: hosted per-save approval (publish()) so apps never hold a credential; DPoP-bound allowance tokens with non-extractable keys; refresh reuse revocation, client binding and shorter lifetimes; shared-origin warnings at registration and consent; versioned, integrity-pinned SDK.
  • App-side: the six curtcox apps switched to publish() and revoke tokens left by their earlier flow on the next load.
  • Rejected: a hidden HashBin iframe holding the credential. Partitioned third-party storage is unreliable across browsers, and co-hosted apps share one embedding origin.

How to avoid it

Use publish() for saves. If you need silent saves, use the SDK's DPoP allowance with a small cap and expiry, and give that app its own origin.

Lessons

Credentials should be HashBin's to hold, not the client's. Registration now asks about shared origins.
