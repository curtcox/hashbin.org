SN-2026-004: A meta Content-Security-Policy also binds srcdoc previews

An editor that previews user HTML in a sandboxed srcdoc iframe cannot add a useful script policy to its own page. The preview inherits the page's policy, so restricting scripts on the editor also breaks users' own scripts in the preview. Pages Online has no Content-Security-Policy for this reason.

Found2026-10-28, while adding policies to the curtcox apps
AffectedPages Online; any editor previewing user HTML through srcdoc
SeverityLow: it removes one layer of defence against bugs in the editor itself
StatusOpen

What was wrong

Documents created from srcdoc share their creator's policy container. A policy that limits script-src to the site would apply to the preview, which must run inline scripts, data-URL scripts and scripts from any CDN the user chooses.

How it was detected

Designing the editor's policy: the preview's needs and the editor's policy could not both be met.

How it can be demonstrated

Add <meta http-equiv="Content-Security-Policy" content="script-src 'self'"> to an editor, preview a page with an inline script, and see it blocked.

How it can be fixed

  • HashBin-side (planned): a HashBin-hosted isolated origin that apps embed for previews and code execution.
  • App-side: load the preview from a document on another origin with its own policy, or from a separate URL rather than srcdoc.

How to avoid it

Plan where user content renders before choosing a policy. Previews that share a document lineage with the editor share its policy.
